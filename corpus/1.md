整体形状：LLM 只做编排、解释和归并去噪，真正的判定交给确定性扫描器（semgrep / 依赖审计 / 配置检查）。这样报告可复核、可回归，也不会因为换个模型就全盘漂移。<br/> <br/>八个阶段：<br/> <br/>阶段 0 定界。四个决策不定，后面全会返工--能力档位（纯被动 / 含授权主动探测 / 含利用验证）、使用者与认证方式、输入形态（上传代码包还是直连 gitlab-ex）、内部源码送内网网关推理的合规结论。<br/> <br/>阶段 1 最薄的贯通切片。骨架 + 网关连通 → semgrep 封装 → LLM 归并层 → 运行落库 → CLI。此时还没有网络入口，也就还没有攻击面，demo 点是 CLI 出一份报告。<br/> <br/>阶段 2 评测集，建在扩能力之前而不是之后。三套分开：能力集（有漏洞样本 + 等量干净样本，ground truth 标注）、护栏集（必须拒绝 / 必须放行 双向都是硬指标）、回归集（线上每个错误当天冻结成 case）。判定优先确定性比对，LLM-as-judge 只用在修复建议质量这类主观项上，且要先用 50 条人工标注校准一致率。dev/holdout 分片，holdout 只在发版门禁跑一次。<br/> <br/>阶段 3 护栏五层：输入层（身份、目标校验、意图分类）、工具层（白名单，无任意 shell / 任意 HTTP 逃生口，主动测试强制人工闸门）、输出层（LLM 输出不进 shell/SQL/路径，secrets 打码，利用代码分级）、资源层（配额、超时熔断）、审计层（append-only）。工具层是最有效的一层，护栏不能只靠 system prompt 写一句「别做坏事」。<br/> <br/>阶段 4 能力扩展，按收益排序逐条加：依赖 CVE → 硬编码密钥 → IaC/配置 → LLM 应用自身安全审查 → 内部规范 RAG。每条过完门禁才合并。<br/> <br/>阶段 5 才第一次开网络入口。FastAPI + 认证（认证是第一个任务不是最后一个）+ 限流 + 极简 UI，UI 上的「真/假阳」标记按钮就是评测集的持续数据来源。绑 127.0.0.1:8090，nginx 加 secagent.park.mcd.ai 独立 server block。<br/> <br/>阶段 6 优化循环，固定五步不许跳：真实失败 → 先变成红的 eval case → 再动 prompt/规则/模型 → 跑 dev 看目标指标涨且误报率没跌 → 过硬门禁再跑 holdout 发版。<br/> <br/>阶段 7 运维与退役条件。<br/> <br/>三个我在计划里设为硬门（一条不过就不发版）的指标：护栏「必须拒绝」100%、注入抵抗 100%、回归集 100%。软指标里最该盯的是干净样本误报率（建议 ≤0.15）--内部工具最常见的死法不是漏报，是误报太多没人用。<br/> <br/>两个和本机环境直接相关的坑已写进约束：一是必须显式关掉 kiro-gateway 回落，它转发到公司外部的 Kiro 后端，等于把被审计的内部源码送出网；二是检索不能用 web-search-plus，它现在只启了 keenable 无密钥公共层，查询串会发到未认证共享服务。知识库走本地 pgvector。<br/> <br/>阻塞的是阶段 0 那四个决策，尤其能力档位--它直接决定要不要建资产台账和授权工单这一整套东西。你定了档位我就可以从阶段 1 开始动手。<br/> <br/>小红书号:402347621
